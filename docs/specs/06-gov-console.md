# 06 政府端：需求熱點與補種優先分數

## 目的

讓承辦看得到需求、排得出順序、交代得了進度。Demo 用桌機開 `/gov`。

## P0

### 熱點清單

每筆許願一列：位置（路名、行政區）、許願原因、澆水數、目前狀態、優先分數。預設依分數排序。

### 補種優先分數

四項各自正規化到 0–1，再加權相加：

| 項目 | 算法 | 資料 |
|---|---|---|
| 市民需求 | 許願的澆水數（取對數後正規化） | 模擬 |
| 遮蔭缺口 | 所在行政區「每公里行道樹數」越低越高（逐段遮蔭率是 P2） | 真實推算 |
| 可行性 | 空樹穴 1.0 > 寬人行道 0.6 > 需會勘 0.3 | 真實推算 |
| 公平性 | 越缺蔭的行政區加分越多 | 真實推算 |

- 四個權重做成滑桿，預設各 25%。拉動滑桿時清單即時重排，有排序變化的動畫。
- 每列可展開，看分數由哪幾項組成。

### 改狀態

- 每列有狀態下拉選單。
- 選「不可種」時必須填原因，不填不能送出。
- 改完寫回 store，市民端即時更新（[05](05-wish.md)）。

### 樹況回報

依路段彙整：每段有幾筆、五類（樹木修剪問題、病蟲害、遮蔭太多或修剪過度、新長枝芽擋路、其他）各幾筆（沒有的類別不列）、類別、樹種與樹籍編號、市民的說明（只有承辦人看得到）、有附照片的相機圖示（照片本身不上傳）。舊版回報（兩類加細項）讀取時換成新的五類，舊細項放在括號裡（對照見 [04](04-tree-page.md)）。每筆回報同時是發包商的養護工單（[08 §8](08-extensions.md)）。

### API 用戶端（2026-10-20，模擬）

`/gov` 下方「API 用戶端」：承辦人建立讓既有系統或廠商用 OAuth 2.0 client credentials 呼叫 API 的用戶端（規格見 [08 §7](08-extensions.md)）。

- 建立：名稱、類型（政府系統／廠商＋哪一家廠商）、scope（依類型預設全勾，可取消）。`client_secret` 只顯示一次（複製鈕），只存 SHA-256 與最後 4 碼。
- 清單：名稱、`client_id`、類型、scope、建立時間、最近使用、狀態；可重新產生 secret（舊的立刻失效，新的再顯示一次）、撤銷。內建示範用戶端不可改。
- 樹況回報清單會顯示 API 標示的「已受理／已駁回：原因」。
- 用戶端與呼叫紀錄只存在這台裝置（模擬）；雲端模式也只寫本機覆寫層，不進 Firestore。

## P1

- 地圖檢視：熱點疊在缺蔭行政區上。
- 「移樹前公告」示範一筆（回應誤砍事件），標模擬。
- 頂部進度條：「把三千棵樹種回來：已種植 N / 3,164」（模擬）。

## P2

- 匯出 CSV、派工、與公園處既有系統串接。

## 不做

- 分級權限。只有白名單帳號（`admins/{uid}`，在 Firebase console 手動建立）能把改動寫進雲端；其他人在 `/gov` 改狀態只寫本機示範覆寫層，標示「示範：只在這台裝置」，不影響雲端與其他人。`/gov` 頁首標示「示範：承辦人視角」。

## 驗收

- [ ] 拉任一滑桿，清單順序在 100 ms 內更新。
- [ ] 分數算法有單元測試，權重全為 0 時不會除以零。
- [ ] 「不可種」沒填原因無法送出。
- [ ] 改狀態後市民端分頁即時更新。
- [ ] 非白名單帳號改狀態不影響雲端。
- [ ] API 用戶端：secret 只顯示一次、可重新產生與撤銷；用 API 改案件狀態後清單即時更新（見 08 §7 驗收）。
